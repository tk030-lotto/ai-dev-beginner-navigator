# 【配布・運用】非エンジニアでも「ダブルクリック一発」で動くWindowsローカルツールの作り方

## はじめに

「とても便利なWebツールができたから、チームのメンバーや初心者の友達にも使ってもらおう！」

そう思ったとき、最大の障害となるのが**「配布と起動のUX」**です。

エンジニアにとっては当たり前の以下の手順も、非エンジニアやプログラミング初心者にとっては「恐怖の儀式」に映ります。

1. ターミナル（黒い画面）を開く
2. `cd` コマンドでフォルダに移動する
3. `npm install` や `npm run dev` を実行する
4. 表示された `http://localhost:5173` をブラウザにコピーして開く

途中でエラーが1文字でも出れば、即座に挫折して使われなくなってしまいます。

目指すべき理想は**「ZIPを解凍して、中にある `ツール起動.bat` をダブルクリックするだけ」**です。

しかし、Windowsのバッチファイル（`.bat`）には、現代のWeb開発者が高確率で踏み抜く**「文字コード（Shift-JIS / CP932）の罠」**が存在します。本記事では、その解決策と堅牢な起動スクリプトの書き方を解説します。

---

## 罠：なぜバッチファイル内の日本語は文字化け・エラーを起こすのか？

VS Codeなどの最新エディタは、デフォルトでファイルを **UTF-8** で保存します。
しかし、Windows標準のコマンドプロンプト（`cmd.exe`）は、日本語環境では **Shift-JIS（コードページ932: CP932）** で動作します。

UTF-8で保存されたバッチファイルの中に日本語のメッセージが含まれていると、以下のような事態が発生します。

1. **画面の文字化け**:
   `echo ツールを起動しています...` が `echo 繧ｿ繝ｼ繝ｫ繧貞錐蜍...` のように化ける。
2. **謎の構文エラー**:
   日本語文字のバイト列の中に、バッチファイルで特殊な意味を持つ文字（`|` や `&`、リダイレクト `>` 等）に合致するバイトが含まれてしまい、「**'○○' は内部コマンドまたは外部コマンド...として認識されていません**」と怒られて処理が異常終了する。

### 解決策：バッチファイルは必ず「Shift-JIS (CP932)」で保存する

どんなに最新のNode.jsやWebツールを使っていても、Windowsの起動エントリポイントとなる `.bat` ファイルだけは、**「Shift-JIS (CP932)」エンコーディングで保存しなければなりません。**

```powershell
# PowerShellからバッチファイルを安全に出力する例
Set-Content -Path "ツール起動.bat" -Value $batContent -Encoding Default
```
※PowerShellの `-Encoding Default` は日本語Windows環境下でANSI（Shift-JIS / CP932）として書き出されます。

## 堅牢な起動スクリプトの設計（ツール起動.bat）

初心者が使うことを想定した場合、バッチファイルには以下の4つの防御策を盛り込む必要があります。

1. **カレントディレクトリの強制同期 (`cd /d %~dp0`)**
   ショートカットから起動されたり、異なる場所から叩かれても、必ずバッチファイル自身のフォルダを作業ディレクトリにする。
2. **Node.jsの存在チェック**
   Node.jsがPCに入っていない場合、エラーログを吐いて落ちるのではなく、「Node.jsがインストールされていません。公式サイトからインストールしてください」と分かりやすく案内して一時停止（`pause`）する。
3. **依存パッケージ（node_modules）の自動判定**
   初回起動時のみ `npm install` を自動で走らせ、2回目以降はスキップして高速起動する。
4. **ブラウザの自動起動**
   サーバーが立ち上がったら、ユーザーにURLを手入力させず、OSの既定ブラウザで自動的にタブを開く。

### 実際のバッチファイル構造例

```bat
@echo off
chcp 932 >nul
cd /d "%~dp0"

echo ===================================================
echo   AI開発初心者ナビ 起動スクリプト
echo ===================================================
echo.

:: 1. Node.js インストール確認
where node >nul 2>nul
if %errorlevel% neq 0 (
    echo [エラー] Node.js が見つかりませんでした。
    echo 本ツールの動作には Node.js が必要です。
    echo 公式サイト (https://nodejs.org/) よりインストールしてください。
    echo.
    pause
    exit /b 1
)

:: 2. 依存関係の確認
if not exist "node_modules" (
    echo 初回起動の準備を行っています (npm install)...
    call npm install
    if %errorlevel% neq 0 (
        echo [エラー] パッケージのインストールに失敗しました。
        pause
        exit /b 1
    )
)

:: 3. ブラウザ自動起動とローカルサーバー起動
echo ブラウザを開いてツールを起動します...
start http://localhost:5173

:: Vite 開発サーバーを起動
call npm run dev

pause
```

---

## ポイント解説

### `where node >nul 2>nul` によるサイレント検査
コマンドの実行結果（標準出力・標準エラー出力）を `nul` に捨てることで、画面を汚さずに `%errorlevel%` の成否（0か1か）だけを安全に判定できます。

### `start http://localhost:5173` のタイミング
サーバープロセスの前に `start` コマンドでURLを投げておくことで、サーバーが起動した直後にOS側のブラウザが該当URLを読み込みに行きます。ユーザーは何の手間もなく、ただ待っていれば画面が表示されます。

## まとめ

どんなに素晴らしいWebアプリケーションを作っても、「最初の起動」でつまずかれてしまえば、その価値は誰にも届きません。

黒い画面やエラーメッセージに不慣れなユーザーに対して、
- **ワンクリックで動くこと**
- **失敗したときは日本語で対処法を教えてくれること**

この「最後の数センチのUX」に気を配ることが、社内ツールやオープンソースツールを広く使ってもらうための最大の秘訣です。
