# 【検索UX】「赤文字が出た」でエラーを特定する——初心者の曖昧な言葉を解釈する同義語検索の実装

## はじめに

検索フォームといえば、「キーワード完全一致」または「形態素解析による全文検索」が一般的です。
しかし、プログラミング初心者向けのツールにおいて、一般的な検索手法はしばしば役に立ちません。

なぜなら初心者は、**「技術的な用語（エラー、例外、ビルド失敗、構文エラー）」を知らないから**です。

初心者が検索窓に入力するのは、以下のような「目に見えた現象そのもの」や「感情」です。

- 「赤文字が出た」
- 「画面が真っ白」
- 「英語ばかりで読めない」
- 「止まった」「動かない」
- 「gitってなに」

本記事では、「AI開発初心者ナビ」に組み込んだ、初心者の曖昧な表現を的確な技術概念に変換する**「同義語展開エンジン（synonyms.ts）」**の実装方法と工夫を紹介します。

---

## 課題：なぜ単純なキーワード検索ではダメなのか？

通常のキーワード検索では、「赤文字が出た」と入力された場合、データベース内に「赤文字」という文字列が含まれている記事しかヒットしません。

しかし、アプリケーション側が提供しているプラグインや記事のタイトルは「ターミナルエラー解決」「ビルドエラー対応」「構文エラー修正」といった専門的な命名になりがちです。

結果として、最も助けを必要としている初心者が**「検索結果0件」**に遭遇し、そこで離脱してしまいます。

---

## 解決策：概念マッピングによる同義語展開

この課題を解決するため、初心者特有の表現と、裏側の技術概念（コンセプト）を結びつける辞書データと展開関数を設計しました。

### 1. フレーズと概念の定義（synonyms.ts）

```typescript
export interface SynonymEntry {
  phrases: string[];    // 初心者が入力しがちな表現
  concepts: string[];   // 紐付ける技術的キーワード群
}

export const SYNONYM_DICTIONARY: SynonymEntry[] = [
  {
    phrases: ['赤文字', 'あかもじ', '赤文字が出た', 'エラーが出た', '動かない', '止まった', '失敗した'],
    concepts: ['error', 'exception', 'failed', 'trouble', 'crash', 'bug', 'エラー'],
  },
  {
    phrases: ['画面が真っ白', '真っ白', '何も映らない', '白い画面'],
    concepts: ['white screen', 'blank', 'render error', '描画エラー', '画面崩れ'],
  },
  {
    phrases: ['英語ばかり', '英語でわからない', '読めない'],
    concepts: ['log', 'trace', 'stack trace', '英語エラー', '翻訳'],
  },
  {
    phrases: ['gitってなに', '保存したい', '巻き戻したい', '戻したい'],
    concepts: ['git', 'commit', 'rollback', 'バージョン管理'],
  },
  {
    phrases: ['公開したい', 'みんなに見せたい', 'webに載せたい'],
    concepts: ['deploy', 'release', 'hosting', 'github pages', 'デプロイ'],
  },
];
```

### 2. 展開ロジックの実装

ユーザーの入力クエリを正規化（小文字化、前後の空白除去）した上で、辞書に登録されたフレーズが含まれているかをチェックします。
含まれていた場合、紐付いている `concepts` を検索クエリの追加トークンとして自動注入します。

```typescript
export function expandSynonyms(query: string): string[] {
  const normalized = query.trim().toLowerCase();
  if (!normalized) return [];

  const matchedConcepts = new Set<string>();

  // 単語分割されたトークンだけでなく、入力文字列全体に対する部分一致も検証
  for (const entry of SYNONYM_DICTIONARY) {
    for (const phrase of entry.phrases) {
      const normalizedPhrase = phrase.toLowerCase();
      // 「赤文字が出たんですけど」のような文章入力にもマッチさせる
      if (normalized.includes(normalizedPhrase)) {
        entry.concepts.forEach(c => matchedConcepts.add(c));
        break;
      }
    }
  }

  // 元の入力文字列と、展開された概念キーワードを結合して返す
  return Array.from(matchedConcepts);
}
```

## 検索スコアリングの工夫

展開された同義語は、プラグインの「タイトル」「説明文」「タグ」との照合時に利用されます。
ただし、ユーザーが直接入力したキーワードと同等に扱うと、ノイズ（検索結果のブレ）が大きくなるため、**スコアの重み付け**を行っています。

1. **完全一致（ユーザー入力）**: スコア 100点
2. **タイトルに含まれる（ユーザー入力）**: スコア 50点
3. **タグに含まれる（ユーザー入力）**: スコア 30点
4. **同義語展開された概念（concepts）にマッチ**: スコア 15点

このように傾斜をつけることで、ユーザーの直接的な意図を最優先しつつ、「赤文字」と入力した際にも裏側で「error」タグを持つプラグインが確実にスコアリング対象へと浮上してきます。

## 実装とテストで直面した注意点

### 1. 長文入力への耐性
初心者は単語（「エラー」）ではなく、「赤文字が出たんですがどうすればいいですか？」と文章で入力する傾向があります。
単なる `===`（完全一致）やスペース区切りの単語分割だけでは検出できないため、`normalized.includes(normalizedPhrase)` による**部分文字列探索**が不可欠でした。

### 2. 文字化けリスク
日本語を含む静的配列を扱う際、エンコーディング不整合による文字化けが混入すると、テストが不意に失敗する原因になります。辞書ファイルの文字コードは厳格に UTF-8 で統一し、自動テスト（Vitest / Jest等）で「赤文字」のクエリが正しく「error」概念を展開できるかをCIで常時監視しています。
